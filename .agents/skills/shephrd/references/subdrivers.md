# Sub-driver mechanics

Use only after an explicit request to activate coordination. No live owner is created by installing the skill.

Main routes faithfully and relays meaningful outcomes; the sub-driver interprets repository-specific ambiguity, plans and supervises ordinary workers. Humans see it as `Sub-driver: <registered repository>` or `Sub-driver: General`. Commands and JSON use `subdriver`; the opaque durable `coordinator:<id>` owner is retained, not renamed. Legacy commands, fields and sessions are compatibility-only; see the [exception inventory and activation requirements](../../../../docs/archive/components/subdrivers.md#compatibility-exception-inventory). Main does not compose detailed worker briefs or resupervise grandchildren. Ordinary direct-driver operation remains supported.

## Main

- `subdriver handoff --repo <registered-repo> --key <stable-key> --request-file <original-text-file> --context "<relevant conversation and actual decisions>" --json` persists intake and starts a bounded session. `--queue` records without starting.
- Outside Pi, provide `--driver-id <main-owner>`.
- `subdriver handoff "<question>" --general-context "<explicit scope and context>" --key <key> --json` starts on-demand general research without repository authority or workers.
- `subdriver reply <request-id> "<actual user reply>" --reply-to <event-id> --key <stable-key> --json` preserves question correlation. A receipt is not an answer.
- A lead returns `handoff` proposals; main routes a sibling request with `--lead-request <lead-request-id>` and relays its result to the nonterminal lead's handoff event. After a result completes a request, route further work as a new correlated open intake with `subdriver handoff --lead-request <completed-request-id>`, preserving the original request, relevant context and actual user replies. No peer-to-peer or recursive ownership.
- Check explicit lead/request/worker links with `subdriver request`, paged `subdriver inspect` and linked `task inspect` before deduplicating or declaring work absent. A rejected dispatch created no worker for that dispatch, not proof that related work is absent. Preserve the original scope and existing task objective/acceptance contract; resolve conflicting delivery scope explicitly, without inventing routing restrictions.

The existing Pi watcher owns notification claims while active. It can activate an already-created dormant owner with pending work even while an earlier main claim remains outstanding and renewing: serialized pump-only passes do not drain another notification or acknowledge early. It presents only correlated sub-driver returns to main. This independent cadence requires the paired CLI/watcher artifact; an old CLI retains drain-coupled activation with an explicit watcher warning. `shephrd wake watch` gives a non-Pi main driver the same pump-only activation while its single delivered claim is outstanding. Run that watcher in a dedicated Herdr pane (with `worker_runtime = "herdr"`) to open sub-driver turns as Herdr tabs; callers over SSH or outside Herdr use `subdriver handoff ... --driver-id <main-owner> --queue` and let the watcher start the turn. Answer with `subdriver reply`, never by typing into a sub-driver tab. After a reboot, start a new watcher in a new pane; it leaves a live turn running and closes its exact endpoint only after the runner exits. A watcher outside a Herdr pane cannot target Herdr and stays headless. Without a watcher, use one bounded wake pass at a natural turn boundary or explicitly `subdriver resume <id>`. Never poll, keep alive, invent work on empty queues or create an independent consumer.

## Sub-driver

The runtime supplies the durable owner and current generation. Use `subdriver request <id>` for full original intake and context before acting. Read the returned commands for omitted events and follow `inspect` paging; omission is never permission to ignore pending work or authority boundaries.

`subdriver dispatch <request-id> "<bounded objective>" --key <stable-step> --feature <unique-feature> --deliverable code|report --acceptance "<criteria>" --json` queues an ordinary task idempotently. Dispatch, inspect the returned task and confirm a successful `worker spawn` receipt/current run before saying assigned or started. Queueing is not running. Replaying a key returns the same task, never a replacement, including after request completion; a new dispatch requires an open request. Carry scoped opt-outs and read-only limits into worker briefs.

Handle your own worker questions and routine recovery through existing task/worker commands after checking current facts. Gate delivery and hold claims on successful command receipts: a busy `worker send` rejection means the follow-up was not queued or delivered and no hold was applied. Annotations and narrative plans are not delivered instructions or changes to the task contract. Acknowledge supplied worker claims only after handling; do not manually drain. Use `subdriver handled <event-id>` for consumed intake/reply records.

Use `subdriver return <request-id> "<concise result or genuine question>" --key <stable-key> --kind question|result|blocker|handoff --json` for main-facing communication. A `result` immediately completes the conversational request: reserve it for actual completion, not assignment or progress. Worker completion is separate and does not complete the request; a result is not an artifact or delivery proof. Late corrections, questions, blockers and handoffs retain correlation without reopening a done request. Route further work through main as a new correlated open intake; ordinary replies to nonterminal lead questions, blockers or handoffs still continue through `subdriver reply`. None grants lifecycle authority.

Each turn gets a fresh harness conversation, at most 48 KiB of Shephrd startup context, 20 input summaries, five worker notices, a 4 KiB checkpoint and a 20-minute deadline. Preserve only immediate continuation and evidence pointers, not task-store copies or transcripts. Read repository instructions and selectively recall existing memory only when enabled and permitted. `memory.enabled=false` applies again at resume. No workflow is selected by discovery.

## Restart

`subdriver ls --all-drivers --json` and `subdriver inspect <id> --json` disclose state without adoption. A replacement main uses `subdriver adopt-request <request-id> --from-driver <old> --driver-id <new> --json` for each relevant request. Never adopt the sub-driver's workers.

Current failures retain held state and publish correlated blockers. Both wake paths atomically compare the observed ID, generation, state and update timestamp before holding; an obsolete running snapshot cannot overwrite normal same-generation completion. See [observation holds](../../../../docs/archive/components/subdrivers.md#restart-and-recovery). Inspect first, then `subdriver recover <id> --generation <exact-generation> --json` after recorded processes and endpoint are absent, followed by `subdriver resume <id>`. Incomplete identity is not permission to retry. `--launch-absent "<evidence and reason>"` is only for explicit operator confirmation that an unrecorded launch is absent; it cannot override a live recorded process or present/uncertain endpoint. Do not use it to guess past uncertainty.

Do not migrate live data or memory, replace installed binaries, change settings, merge or release merely to enable this role.
